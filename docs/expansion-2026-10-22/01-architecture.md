## Part 1 · What exists now

### 1.1 Lesson and item schema

**Item types.** There are seven, all in `js/engine/items.js`: `mc`, `ms`, `ebsr`, `dropdown`, `hottext`, `order` and `match`. Each type provides `blank`, `render`, `answered`, `score`, `narrow`, `outline`, `answerText`, `describe` and `narrowText` (items.js:1-14). Scoring rules are in SPEC §5 (docs/SPEC.md:143-151).

Across the 99 lessons in the manifest, the lesson items (practice, test and testB) break down as follows: mc 444, dropdown 197, hottext 137, match 129, ms 95, ebsr 54 and order 20.

**Item text fields.** These are required by `verification/check-content.js:133`:
- `prompt`
- `clue`: one strategy line that must not contain the answer (check-content.js:151, plus a giveaway warning at :152-162)
- `why`: the walk-through, which names the answer (it is warned at :150 when it does not)
- optional `stem` and `figure`

There is **one authored hint level**. The other levels are generated by the engine.

**Help ladder in practice** (`js/engine/player.js:318-338`):
1. "Hint 1 of 3" shows `item.clue`.
2. "Hint 2 of 3" runs `T[type].narrow(ctx)`. This changes the controls: for mc it crosses out two choices and disables them (items.js:118-126). It can also clear the child's pick.
3. "Let's walk through it" shows `item.why` followed by "Now you choose it.", and runs `outline()`, which highlights the correct choice (`.is-hint`).

So the third step reveals the answer. Nothing is called "Show me how" in practice. That name exists only in the test review (player.js:514-531), where it gives the clue, then `narrowText`, then `why`, and then shows "The answer: …".

**Feedback and retries** (player.js:340-367):
- **Correct:** "That's right!" with `item.why`. The item locks.
- **Wrong:** "Not quite" with "Try again, or press Help me for a hint." When the answer is partly right, the feedback also says "You got part of it (x of y points)" and adds `partialNote`.
- **Retries:** unlimited. After the **third** wrong Check the ladder opens automatically to the walk-through (player.js:353-355). Nothing records that the answer was shown.

**First-try against helped.** `run.state[i] = { help, wrong, solved, firstTry }` lives only in memory (player.js:191). `firstTry` is set on the first Check (true only if the answer was fully right with no help, :344). At the end, `practiceDone()` reports "You got N of M right on your first try without help" (player.js:403-418). It stores only:
- `prog[k].practiced` or `prog[k].tried`, as booleans (skills.js:218)
- `history.state.ppDone = { set, mode, n, first }` (app.js:68-71)

**Nothing is stored per practice item:** no response, hint count or reveal. A reload starts the set again at question 1. Confirmed in the browser: `practice.reload` gives pos 0 with every `help` value at 0, and `practice.ls_mid` shows no new key.

### 1.2 Practice sets, the Together and Try split, and counts

- **Registration.** `addLesson()` (skills.js:27-63) turns each lesson into ordinary sets: `SK:<key>:p` (Practice Together), `SK:<key>:y` (Try It Yourself), `SK:<key>:t` (form A) and, when `testB` exists, `SK:<key>:tB`.
- **Split.** The split is `half = P.length >= 4 ? Math.ceil(P.length/2) : P.length` (skills.js:33). Together gets the first `half` items and Try gets the rest.
- **Allowed sizes.** check-content requires **practice to have 4 to 7 items and test 4 to 6** (check-content.js:265-268). The **cap is 7**. The only exception is a hands-on lesson with `activity` or `check` (:267).
- **Current totals.** There are 95 lessons with practice, holding 520 practice items: **298 Together and 222 Try**, so Try has two or three items per lesson. There are 489 form A items, and 67 form B items across 13 lessons. Twenty-three lessons have a `write` card and three have a `speak` card. Four hands-on lessons have neither practice nor a test: 3.F.F.1.b, 3.F.F.1.c, 3.F.H.4.a and 3.F.H.4.b.
- **Try It Yourself behaviour.** `run.tryMode` hides Help me until one wrong Check (player.js:301). The feedback then says "Try again. Help me is now on if you need a hint." (:357). The step card reads "Help me unlocks after one try." (skills.js:914). Confirmed in the browser: `try.start` shows `help:false`.
- **Chain.** `:p` → `:y` → the check that the site picks (`next`, skills.js:54-55; player.js:649-652).
- **Run modes.** A skill's practice sets never run as a test, and its checks never run as practice. `skillMode()` enforces this (player.js:543-548, the RD-4 rule).

## Part 2 · Design (not implemented)

### 2.1 A standard destination: `#std/<code>`

#### Resolving a code

A new module, `js/std.js` (`PP_STD`), has `resolve(input)`. It returns `{ code, kind }` or null:

| Input | Resolves to | kind |
|---|---|---|
| A leaf code in `PP_STANDARDS`, such as `3.T.T.1.b`, a GUM row `3.L.GC.1:M:…` or `K-12.P.EICC.1.a` | itself | `leaf` |
| A parent in grade 3 form, such as `3.T.T.1`, `3.L.GC.1` or `K-12.P.EICC.1` | itself | `parent` |
| The GaDOE band form, such as `3-5.T.T.1` | `3.T.T.1`, with `replaceState` to the canonical address | `parent` |
| `3.L.GC.1:M`, `:R`, `:I` or `:C` | one GUM level | `gum-level` |
| A lesson key, such as `TS-CE` | not resolved here, because `#skill/TS-CE` already works | — |
| Anything else | the existing not-found behaviour (app.js:343-352) | — |

#### New data file

`js/data/std-groups.js` (`PP_STD_GROUPS`) has one entry per parent code. The standards-alignment and instructional-design agents author it.

```js
{ code: "3.T.T.1", band: "3-5.T.T.1", name: "Narrative Techniques",
  official: "Explain, analyze, and use narrative techniques to shape understandings.", page: 31,
  order: ["3.T.T.1.b", "3.T.T.1.c", "3.T.T.1.a", "3.T.T.1.d", "3.T.T.1.e"],   // component codes, recommended order
  lessons: { "3.T.SS.1.a": ["TS-SEQ","TS-CE","TS-PS","TS-CC","TS-DESC","3.T.SS.1.a"] },   // optional per-code lesson order when a code has more than one lesson
  review: "RV-3.T.T.1",                       // standard or skill-group review set (2.5), optional
  observe: "Retelling and writing a story need a grown-up to listen or read (3.T.T.1.e)."   // optional
}
```

`check-content.js` checks this file in four ways:
- `official` and `page` match a new transcription, `docs/audits/work/official-gr3-parents.json`.
- `order` lists exactly the leaf codes under the parent.
- Every key in `lessons` exists.
- `review` resolves.

#### Page content

There is one new screen, `<section id="screen-std">`, with an `h1#std-title` that has `tabindex="-1"`. **Rendering writes nothing.**

**Narrow code.** A narrow code is one leaf with exactly one main lesson and no other main lessons. Its page has these sections, in order:
1. **Code and title.** The eyebrow shows the code, using `codeLabel()` for GUM rows. The `h1` is the lesson title.
2. **Georgia's official wording, with page.** It uses the existing `x.official` and `x.page` fields. Below it, smaller, sits the parent standard's statement, linked to `#std/<parent>`.
3. **What your child will learn.** This is `s.plain` plus the lesson's `teach.big`, and the "On the test" or "Classroom skill" tag (reusing `TESTED`, skills.js:267-274).
4. **The lesson.** The primary button is "Start the lesson", or "Continue at <step>" when `firstOpenStep()` (skills.js:338-345) says the lesson has started. Below it is a line: "Also practiced in: …" (lessons that list the code in `codes`).
5. **Practice.** It lists Practice Together (n questions) and Practice on my own (2.2), with honest progress: "Set 1 finished, set 2 started, set 3 not started".
6. **Assessment.**
   - The skill check, with its number of questions, its points and how many forms it has. With two forms it says: "The next check uses form B, with different questions." With one form it says: "Each try uses the same questions."
   - The skill-group review of the parent code, when there is one.
   - The cumulative review parts that include this code.
   - "Practice Test 1 has N questions on this code", computed from item `std` as in `setsFor` (parents.js:87-93).
7. **What a grown-up needs to watch.** This is derived from `write`, `speak`, `activity` and `check`, plus the group's `observe`.
8. **Progress on this device.** It shows `displayState()` (skills.js:224-234) word for word, the last check's date and score, and the practice summary. It ends with: "This shows what was done on this device. It is not a Milestones score." It never uses "mastered".
9. A collapsed draft ALD (Proficient), reusing the skill page's text and caveats.

**Broad, parent or multi-lesson code.** This covers a parent code, a GUM level, or a leaf with more than one main lesson (3.T.SS.1.a). The page has:
- the parent's official statement and page, and the plain name
- an ordered list of components, each a row with:
  - a code link to `#std/<leaf>`
  - the plain text
  - one or more lesson buttons (separate elements, never nested)
  - the `displayState` label
- **"Suggested start: the first lesson in this order without a passed check on this device."** This is computed and static order, never placement.
- the review: what it measures, what it does not measure, and its last result
- what needs a grown-up's evidence

Two codes need special handling:
- **GUM 3.L.GC.1** is grouped by level: Master and Reinforce ("on the test, writing part") first, then Introduce and Continue ("practice this year; not on the grade 3 test").
- **Practices codes (K-12.P…)** show the habit content now built in `renderPending` (skills.js:1093-1103), with "A grown-up observes this. There is no scored check." No multiple-choice substitute is added.

### 2.2 "Practice on my own": an extension of Try It Yourself

On 3.T.T.1.c that is exactly P1 to P3; P4 to P6 appear only in core set 1. check-content enforces it (rule 10b) and `verification/practice-own.py` checks it in the browser. #### 2.2.1 Controls on every core item (player "own" mode)

The player gets `run.own = !!set.own`. It runs in practice mode, so it is never scored and never offered as a test. `#q-help` is hidden. Four controls are added to `.q-controls` (index.html:253-258):

| Control | Id | Behaviour |
|---|---|---|
| **Check my answer** | `#q-check` (reused) | Full points mean the answer is solved: "That's right!" with `why`, and the item locks. Otherwise "Not quite" (with the existing partial line). A **retry is allowed**. After **two** wrong checks, Check is disabled with "Two tries used. Ask for a hint or press Show me how." Taking a hint re-enables one more check. This replaces the automatic walk-through after the third wrong check (player.js:353) in this mode, so nothing reveals the answer without the child asking |
| **Give me a hint** | `#q-hint` | Shows the authored `hints[0..2]` one per press, labelled "Hint 1 of 3", "Hint 2 of 3" and "Hint 3 of 3". It never runs `outline()`. It runs `narrow()` only when the item opts in with `hintNarrow: 2`. After the third hint the button is disabled and reads "No more hints". Focus moves to the new hint, as in player.js:334-337 |
| **Show me how** | `#q-how` | Visible from the start, before any wrong answer. The visible label is "Show me how (shows the answer)". It shows `how` steps as a numbered list, then "The answer: …" (`answerText`), then `why` and the optional `misconception`. It runs `outline()`. **It marks the item "Answer shown" permanently.** Afterwards the child may still enter the answer, but the status does not change. If pressed after a correct answer, it only shows the steps: it is recorded as `howAfter` and the status is unchanged |
| **Try a similar question** | `#q-similar` | Shown after Show me how, and also after any finished item when a similar item is available. It opens a **separate** item from `L.similar` in the same player, headed "Extra question (not one of the fifteen)", with the same four controls (Similar is hidden on it). On Next it returns to the core sequence at the following item. It is recorded under the similar map, never over the core item |
| **Next** | `#q-next` | After the item is solved or its answer shown. The child can also skip; the item stays "Not finished". **Previous** (`#q-prev`) is shown in this mode, so the child can move within a set |

**Choosing a similar item (lead decision, 2026-10-23; replaces the earlier "never offer a used one").** The choice is deterministic and uses only the similar items whose `like` names this core item:
1. the first of them, in bank order, that has not been used yet;
2. if every one has been used (earlier in this sitting, in an earlier sitting, or on a second pass through a finished set), the one used **least recently**, by the record's new `t` field (milliseconds; `d` for older records).

A core item with no similar item in its own list hides the button; there is no fallback to another core item's list. Used state lives in `pp.practice.v1` (`s[<similarId>]`) and persists across sittings, which is why a "never offer a used one" rule left a returning child with no button. A similar question offered again is a **new attempt**: on its first save, the earlier attempt moves into the record's `past` list (newest last, at most ten). The record's own fields keep their meaning (the latest attempt), and no help history is erased. Tests: practice-own N.1 (one sitting, all fifteen in order) and N.2 (a second sitting after finishing the set).

**At the end of a set**, `practiceDone` (player.js:403-418) has an own-mode branch:
- It shows the set summary by category.
- The buttons are "Go on to set 2" (primary), "Back to the lesson", and on set 3 "Take the skill check" (which uses `checkFor`).
- `markDone` gets `{set, mode:"try", own:true}`, so Forward or a reload shows the "already finished" stage. For own sets, that stage offers "Look back at this set" and "Go on to the next set" (`finished()`, player.js:589-616).

#### 2.2.2 Constructed-response core items

A new type, **`cr`**, may be used only in `core` and `similar`:

```js
{ id, type:"cr", prompt, stem?, rows:4, sample:"…", criteria:["…","…"], hints:[…3], how:[…], why? }
```

- **Check my answer** becomes "Compare with the sample". It shows `sample` (labelled "One good answer. Other answers can also be right.") and `criteria` as labelled checkboxes ("Did I…") for the child and a grown-up.
- **It is never scored.** Its status is "Written and checked against the list" or "Not finished". It is never counted as "right".
- `T.cr` implements `score()` as `{points:0, max:0}`. check-content fails `cr` in `test` or `testB`. Guard section 2 excludes `cr` items (2.7).

#### 2.2.3 Per-item status (one definition, used everywhere)

Status is **derived** from stored facts, never stored as a label:

| Status (shown words) | Rule | Precedence |
|---|---|---|
| **Answer shown** | `x` (Show me how pressed before the item was solved) | 1 (highest; never erased) |
| **Right with hints** | `ok` and `h > 0` | 2 |
| **Right after another try** | `ok`, `h = 0` and `w > 0` | 3 |
| **Right on the first try** | `ok`, `h = 0`, `w = 0` and not `x` | 4 |
| **Written and checked** (`cr` only) | `cr.done` | — |
| **Not finished** | none of the above | — |

`ok` means full points, so a partly right answer counts as a wrong try. A hint taken after solving is impossible, because the button is hidden. The history stays visible: once `w`, `h` and `x` are set they never go down. Clearing them is possible only through "Start this set again", which moves the old record to a history field instead of deleting it (see 2.2.4).

#### 2.2.4 State: a new versioned key, `pp.practice.v1`

```js
{ "v": 1,
  "l": {                                   // by lesson key
    "3.T.T.1.c": {
      "rev": "1",                          // the lesson's core.rev when this record was written
      "at": { "set": 2, "pos": 3 },        // last place (set 1-3, question 1-5)
      "i": {                               // by core item id (site-unique, SK-…)
        "SK-TT1c-C07": { "r": {"v":2}, "w": 1, "h": 2, "x": false, "ok": true, "howAfter": false, "d": "2026-10-22" },
        "SK-TT1c-C12": { "cr": { "text": "…", "checks": [true,false,true], "done": true }, "h": 0, "x": false, "d": "…" }
      },
      "s": {                               // similar items, separate from the fifteen
        "SK-TT1c-S02": { "for": "SK-TT1c-C07", "r": {"v":1}, "w": 0, "h": 0, "x": false, "ok": true, "d": "…" }
      },
      "old": [ { "d": "…", "set": 1, "i": { … } } ]   // only when "Start this set again" is used; last three kept
} } }
```

**Stored response values** (`r`) use the engine's own index space: `data-i` choice indexes, slot indexes, refs and `opt:n`. They do not depend on the shuffled display order (items.js:13-14, 109). On resume the order is shuffled afresh, which is acceptable, and the saved choice is restored by its index.

**Load** follows the UX-002 pattern (skills.js:79-88):
- a map with no prototype, and unsafe names excluded
- each lesson record and item record must be an object
- each numeric field is clamped (`w` and `h` are whole numbers from 0, and `h` is at most 3)
- `x` and `ok` must be booleans
- unknown fields are kept
- **Malformed JSON is treated as empty, and the raw value is never overwritten until the first successful save that follows a real child action.** Rendering never writes.

**The "tried" step mark.** `pp.progress.v1[k].tried` is set, through the existing `mark(k,"tried")`, only when all fifteen items are not "Not finished". Nothing else in `pp.progress.v1` is written. Specifically, no `mastered`, `best`, `tries`, `attempts` or `passedAt` is ever written, and practice can never award a pass.

Three changes elsewhere read the new store:
- `status()` (skills.js:257-263) gains a read-only `|| PP_PRACTICE.any(k)` for "started", so Practicing shows correctly.
- The Try step's done tick (skills.js:341, 743) on a lesson with `core` uses `PP_PRACTICE.complete(k)`. A `tried` left by the old two-or-three-item Try still counts for "Practicing", but does not tick the new fifteen-item step.
- The Learning Path note (path.js:198) and the "How a lesson works" line (app.js:140) are worded per lesson kind until every lesson has moved over.

**Revision.** `core.rev` is a string the authors bump when core items change materially. **Implemented (ENG-06):** every core and similar item has a content signature (FNV-1a of its type, words, choices, key, points and passage text; hints, Show me how and explanations are left out) computed at registration. Each saved record stores `sig`. A record whose `sig` differs from the current item's is read as not started, and its facts move to the record's `prev` on the next save. Records saved before signatures existed have no `sig` and are kept as they are. The picker says "This practice was updated. One question changed, so it starts fresh. Your earlier answers to the other questions are kept." when any record is stale, and only "This practice was updated. Your earlier answers are kept." when `rev` changed but no question did.

**Size.** A worst case of 95 lessons × 20 records × about 120 bytes is about 230 KB. A full store (`QuotaExceededError`) is handled like a blocked one.

#### 2.2.5 When saving fails

`js/practice.js` keeps a per-visit `session` Map, as in writing.js:15-85.
- **On load** it runs a test write, like path.js:22-26.
- **When writes fail:**
  - The state stays in memory for the page visit.
  - The set picker and the player (in a `p#q-storage` with `role="status"` under the controls) say: **"Saving is unavailable. Your practice answers are kept only while this page stays open. If you reload or close it, this practice starts again from the beginning."**
  - The "You can stop and come back" line is replaced, never promised.
- **When a later write succeeds**, the notice is removed and the session copy is flushed.
- **When the stored value is damaged**, the notice says: "Saved practice could not be read, so it starts fresh. Nothing else was changed."

There is no `beforeunload` prompt for practice, because the risk is low and a prompt would be noisy. The notice is enough.

### 2.3 Item and lesson schema additions (backward compatible)

### 2.5 Assessment at three levels

**Level 1: lesson checks.** These exist already (form A, and form B on 13 lessons). Unchanged except for 2.4.

**As built (lead decision, 2026-10-23, ENG-09).** The lead chose to draw review and cumulative questions only from **ACCEPTED** lessons' scored checks (`test`/`testB`, never written `cr` items), not new items. `js/data/accepted.js` lists the accepted lessons; check-content fails when it disagrees with `batches/STATUS.md`. `js/review.js` builds, at load and with no storage writes: one review per parent standard (`RV-<parent>`, split into parts of at most five components); cumulative curriculum parts for four ELA areas (`CR-lit`, `CR-info`, `CR-write`, `CR-lang`; a part exists only when its area has an accepted lesson, otherwise the hub says it is not available yet; one question per accepted lesson, preferring questions not used by a standard review); the hub `#review` (curriculum review, state-test practice linking PT-1, writing tasks, observed by a grown-up); and the coverage map `#coverage`. Review sets are addressable in `PP.byId` but are not added to `PP.sets`. Because the questions come from the lessons' checks, the review page says so ("your child may have seen some of them"). Results are saved as `pp.review.v1 = { v:1, r: { <setId>: { a: [ { d, got, max, n, comps } ] } } }`. The rest of this subsection is the original recommendation, kept for the record.

**Level 2: standard or skill-group reviews. Recommendation: new, reviewed items, not samples.**

Why not samples:
- Sampling from component lessons' check items reuses questions whose answers the child may already have seen (`afterAnswers`).
- Sampling core practice reuses items practised with hints.
- Either way, the review would stop being fresh material and would weaken form independence.

The recommended design:
- A file `js/data/reviews/RV-<parent>.js` calls `PP.addReview({…})`, which registers ordinary `kind:"review"` sets.
- Each item carries `comp: "<leaf code>"`.
- There are at least two items and three points per applicable component, so component rows qualify under 2.4.
- When there are more than six components (3.L.GC.1 Master and Reinforce has 26 rows, and 3.T.SS.1 has four leaf codes but six lessons), the review is split into labelled parts (`RV-3.L.GC.1-P1` and so on). Each part is submitted on its own, so it can be done in separate sessions.
- Each review declares `measures: [codes]` and `notMeasured: [{code, why, evidence}]`. For example, 3.T.T.1.e writing a story is not measured; its evidence is the lesson's writing activity, scored by a grown-up. The standard page shows both lists.

Results go in a **new key, `pp.review.v1`**:

```js
{ v:1, "RV-3.T.T.1": { attempts: [ { d, got, max, rev, form, parts:{…}, comps:{ "3.T.T.1.b":[got,max] } } ] } }
```

These results never touch `pp.progress.v1` and **never set a pass**. They are shown as "Review taken on <date>: x of y points".

**Level 3: the cumulative ELA review.** This reuses the form architecture (1.6). The hub is reached from `#mixed`. It is a fifth section card, "Cumulative review", in `PP_SITE.sections`, and **guard 1.1b must change from four to five**. Alternatively, it can be a link above the four cards, which keeps 1.1b unchanged; the lead should choose.

The hub has four clearly labelled kinds:

| Kind | Content | Scoring |
|---|---|---|
| **Curriculum review** | New sets `CR-1-READ`, `CR-1-LANG` and `CR-1-REV` (`kind:"form"`, `section:"review"`), one part per sitting | Points, and component rows under 2.4 rules. Saved in `pp.review.v1` |
| **State-test practice (blueprint-shaped)** | The existing PT-1, plus later forms | Points. Its result is saved in `pp.review.v1` too (today it is not saved) |
| **Writing tasks** | W-TASK-01 and W-TASK-02 (writing.js) | A grown-up scores them with the rubric. They are never scored automatically |
| **Observed by a grown-up** | Links to the fluency, cursive, speaking and habit pages | Ticks and notes, never a score |

The hub shows which parts are done, with dates, and never a combined "ELA mastery" figure. Every review result carries the line "A practice score on this site. It is not a Milestones score or achievement level."

**Assessment coverage map.**
- A generator, `verification/gen-assess-map.js` (Node, read-only), joins `standards.js`, lessons (practice, core, test and testB), reviews, PT-1, tasks and habits.
- It writes `docs/expansion-2026-10-22/assessment-coverage-map.csv` with these columns: code, tested, lesson check items and points (A and B), review items, cumulative review items, PT-1 items, writing task, observation, and "not assessed here (why)".

### 2.6 Validation: new check-content.js rules

These are added to `verification/check-content.js` after the lesson block (:224-319). Legacy lessons without `core` are unaffected unless stated.

1. **Applicability.** Every manifest lesson with a `test` must have `core` **or** `coreException`. Also, the lesson must be listed in `docs/expansion-2026-10-22/practice-exceptions.json` exactly when it has `coreException`. During migration this is a **warning**. It becomes a **failure** with `--release`, and the release gate runs with that flag.
2. **Structure.** `core.sets` has exactly three sets, each with exactly five items, which gives 15 items. `core.rev` is a non-empty string.
3. **Unique ids.** Ids are unique across core, similar, practice, test and testB, and across the whole site (the existing `seenItem`), and start with `SK-`.
4. **Hints.**
   - Every core and similar item has `hints` with exactly three non-empty, distinct strings.
   - None contains a choice's answer text: reuse `noLeak` (check-content.js:151) on each hint.
   - The giveaway check (:152-162) runs on h1 and h2.
   - A warning is raised when h1 is longer than h3, which suggests the hints do not get more specific.
5. **`how`.** It has two to five steps, and the steps or `why` must name the answer (reuse `mustName`, :150, as a failure for core items). Choices are never referred to by position (:148).
6. **Item rules.** All existing `checkItem` rules apply. `cr` requires `sample` and two to five `criteria`, and **fails in test or testB**.
7. **Distinct practice.**
   - Fail when two core items share a stem or are the same question (reuse `stemOf` and `whole()`, :296-297).
   - **Warn on trivial variants**: proper names are replaced with a placeholder, and the stems and choices are compared again.
8. **Separation.**
   - Core and similar passages must not be used by test or testB items. This is a **failure**; the existing practice rule is only a warning (:278-279), and there are **0 such reuses today**.
   - Core items must not share an id or stem with test items.
9. **Similar items.**
   - Every `like` id exists in core.
   - Every core item is covered by at least one similar item. **Lead decision: an uncovered core item is a warning, not a failure**, and the player hides "Try a similar question" on it.
   - There are three to fifteen similar items.
   - Similar items have no id or stem shared with core.
10. **Practice Together** on a core lesson has two to five items. Legacy lessons keep 4 to 7.
    - **10b (lead decision).** Together on a core lesson is `practice` minus the `{ref}` items. Every `ref` must name an item in `practice`, no item may be referenced twice, and a referenced item must not also appear as a full core item. The checker prints the Together ids it derives, so a reviewer can confirm that 3.T.T.1.c shows exactly P1 to P3.
11. **Review ledger.** `docs/expansion-2026-10-22/review-ledger.json` maps `lessonKey → { core:{rev, hash, reviewers:[…], date}, similar:{…} }`.
    - The checker computes a SHA-256 hash of each lesson's core and similar items (ids and content) with Node `crypto`.
    - A **mismatch, or a missing entry, fails with `--release`** and warns otherwise.
    - This proves the reviewed content is the shipped content, and that authors did not review their own work (the reviewer names are listed, and the lead checks them against the author list).
12. **Assessment versions.**
    - `verification/assessment-versions.json` holds a hash per form (`<key>:A`, `<key>:B`, review sets and CR sets) together with its `rev`.
    - A changed hash with an unchanged rev **fails**.
    - The file is created once from today's content, with every rev at "1".
13. **Standard groups** (2.1). Official parent wording matches the transcription, and `order` and `lessons` are complete and resolve.
14. **Reviews.** Each component in `measures` has at least two items and three points. Every `notMeasured` entry has `why`. Item `comp` is one of `measures`.
15. **Summary line** (:443-445). Add the counts of core, similar and review items.
